# 功能设计上的教训

> 创建时间：2026-05-26

## 1. 邮件只发摘要没发全文

**背景**：第一次写每日知识推送，图省事只截取前 500 字作为预览。

**用户反馈**："大哥，推送能不能把笔记内容都推出来啊"

**问题**：替用户决策"看多少"而不是让用户决策。知识推送的价值在完整内容，摘要=阉割。

**解决**：重写 `md_to_html()` 函数，做完整的 Markdown → HTML 转换，保留整篇笔记。

**教训**：做信息类功能时，默认给完整内容，摘要只是可选项。砍内容≠精简，砍内容=偷懒。

## 2. 笔记编号两位数隐患

**背景**：笔记用 `第1篇`、`第2篇`...`第10篇` 编号，20 篇时没问题。

**预判**：到 100 篇时，字符串排序会变成 `第100篇` → `第10篇` → `第11篇` → ... → `第1篇`，全乱。

**解决**：趁现在才 20 篇，全部改成三位数零填充：`第001篇`、`第010篇`、`第100篇`。19 个文件批量重命名，连带修正了 `发送精选笔记.py` 里的硬编码路径。

**教训**：编号系统第一天就要考虑规模。两位数撑不过 99，趁早改成本最低。这种坑越晚改越疼——等 50 篇以上再批量重命名就麻烦了。

## 总结：设计三问

每次做自动化功能前问自己：
1. 用户拿到的是完整信息还是被阉割的？
2. 现在的规模能撑到 10 倍、100 倍吗？
3. 如果有 bug，用户自己能修还是只能等我修？
